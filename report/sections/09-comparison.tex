\section{Comparative Study}
\label{sec:comparison}

We compare the schemes in two ways. First we set the paper's search against the counter index, using our own
measurements. Then we place QPASE among related password-based schemes, using the paper's own comparison.

update and file encryption, so the table covers only search and what it needs.

The counter index wins on the server side. Its search key stays on the device, it gives forward privacy, and its
slowest server searched \ScalingSpeedupMin{} to \ScalingSpeedupMax{} times faster in our runs. Its index row is
also much smaller than the paper's $Ct$. It pays for this with a second round trip, a counter table to store and
upload, and a request that grows with $c_w$. Both schemes leak the search pattern. Both also show the server which
files a search returns: QPASE when the server finds the matches at R2, and the counter index when the user fetches
them at R4. For the user, a search costs the same in both schemes, because both run $1 + c_w$ PRF chains.

Three points stand out in the paper's comparison. QPASE is the only scheme in the table that is both quantum
resistant and lets the user retrieve data. Only QPASE and QPause model passwords with Zipf's law, which matches
how people choose passwords better than a uniform distribution~\cite{wang2017zipf}. And the lattice schemes need
no exponentiations at all, so their entries read $0 / 0$.

The last column needs care. It counts only exponentiations, so it says nothing about the lattice operations that
replace them. In our implementation a single lattice PRF chain takes \AxMedian, and every user-side phase spends at
least \ChainShareMin{} of its time in such chains (\cref{sec:evaluation-qpase}). A $0 / 0$ entry therefore does not
mean that QPASE is cheap. It means that its cost lies in a different operation, which this table does not count.
Table~V also does not compare search privacy. None of its columns covers forward privacy, the property the
counter index adds.
